2) สิ่งที่เปลี่ยนในโครงสร้าง
--------------------------------------------------
เพิ่มชั้นตีความเหตุการณ์ขนาดเล็ก (chat2work/extractors/semantics.py) ทำ 3 อย่าง:
1. แบ่งข้อความเป็นอนุประโยค (clause)
2. จัดสถานะของอนุประโยคที่มีเหตุการณ์ เป็นหนึ่งใน:
   - ยืนยันจริง (asserted)
   - ปฏิเสธ (negated)
   - มีเงื่อนไข (conditional)
   - อนาคต (future)
   - คำถาม (questioned)
   - คำพูดของคนอื่น (reported)
   - ไม่แน่ใจ (uncertain)
3. ระบุเป้าหมายของเหตุการณ์:
   การซื้อ / เอกสาร / ข้อมูล / การชำระเงิน / นัดหมาย

ก่อนเปลี่ยนสถานะดีล ปิดคำรับปาก เลื่อนนัด หรือเลือกยอดรายได้ ระบบจะจัดประเภทเหตุการณ์ก่อนเสมอ
- นับว่า "ส่งแล้ว / ได้รับแล้ว / โอนแล้ว / ทำเสร็จแล้ว" เฉพาะเมื่อยืนยันจริงเท่านั้น
- การปฏิเสธและการยกเลิกอ่านทีละอนุประโยค
  และตัดคำสุภาพกับสรรพนามออกก่อน เช่น "ขอโทษครับ", "ผม"
- ไม่ได้แก้ด้วยการ blacklist ข้อความเฉพาะ


3) ปัญหา 9 กลุ่ม: ก่อนแก้ / หลังแก้
--------------------------------------------------
[1] ร้านเสนอข้อมูลแบบประโยคธรรมดา แล้วถูกนับเป็นยอดขาย
    ตัวอย่าง: "ส่งแคตตาล็อกให้ครับ" / "เอาครับ"
    ก่อน: ยืนยันยอดขาย
    หลัง: เป็นการตอบรับข้อมูล ไม่นับเป็นยอดขาย

[2] ปฏิเสธหลังตกลงซื้อแล้ว แต่ระบบไม่สนใจ
    ตัวอย่าง:
      "ผมไม่ซื้อครับ"
      "ขอโทษครับ ไม่จ้างครับ"
      "ไม่ซื้อครับ ขอบคุณที่ส่งรูปมาแล้วนะครับ"
    ก่อน: ยอดขายยังยืนยันอยู่
    หลัง: ดีลถูกปฏิเสธ และยังเก็บประวัติการตกลงเดิมไว้

[3] ประโยคเงื่อนไข / อนาคต / คำถาม ปิดคำขอใบเสนอราคา
    ตัวอย่าง:
      "ถ้าส่งใบเสนอราคาแล้วจะโทรแจ้ง"
      "พรุ่งนี้จะส่ง… แล้วโทรแจ้ง"
      "ส่งแล้วใช่ไหม"
    ก่อน: ปิดคำขอ
    หลัง: คำขอยังเปิดอยู่

[4] ขอให้ยังไม่ต้องส่ง แต่ระบบเสนอทั้ง "ส่งเลย" และ "รอก่อน"
    หลัง: เสนอแค่ "รอให้ลูกค้าแจ้งก่อน" และยังเก็บคำรับปากของร้านไว้
          รองรับการขอเลื่อนที่อยู่ในคำขอเดียวกัน
          พอลูกค้าบอกให้ส่งได้ ระบบเสนอให้ส่งอีกครั้ง

[5] ประโยคเงื่อนไขหรือการโอนบางส่วน ปิดคำรับปากการชำระทั้งหมด
    ตัวอย่างเงื่อนไข: "ถ้าโอนแล้วจะส่งสลิป"
      หลัง: ไม่นับว่าแจ้งโอน
    ตัวอย่างโอนบางส่วน: "โอนแล้ว 1000 ที่เหลืออีก 4000 จะโอนพรุ่งนี้"
      หลัง: บันทึกว่าโอนแล้ว 1,000
            และสร้างคำรับปากยอดคงเหลือ 4,000 พร้อมกำหนด "พรุ่งนี้"
    การโอนที่ลูกค้าแจ้ง ยังถือว่ายังไม่ได้ตรวจสอบกับธนาคาร

[6] เลื่อนเรื่องอื่น แล้วนัดติดตั้งถูกเลื่อนไปด้วย
    ตัวอย่าง: เลื่อนส่งรูป / เลื่อนวันโอน / เลื่อนวันส่งใบเสนอราคา
    ก่อน: นัดติดตั้งถูกยกเลิก
    หลัง: นัดติดตั้งยังอยู่เหมือนเดิม

[7] ประเภทของจำนวนเงินผิด ทำให้ยอดโอกาสรายได้เพี้ยน
    ตัวอย่าง: "ลดให้เหลือ 17000"
      ก่อน: ยอดยังเป็น 18,500
      หลัง: ยอดเป็น 17,000 (ราคาสุทธิใหม่)
    ตัวอย่าง: "รวมค่าแรงไว้แล้ว 1500"
      ก่อน: ยอดกลายเป็น 1,500
      หลัง: ยอดยังเป็น 18,500

[8] "ติดตั้งเสร็จแล้วมั้ง" ถูกนับว่าเสร็จจริง
    หลัง: ยังติดตามงานต่อ และเสนอให้ตรวจสอบว่าเสร็จจริงหรือไม่

[9] ยกเลิกใบเสนอราคา แต่ระบบยกเลิกการซื้อด้วย
    ตัวอย่าง: "ยกเลิกใบเสนอราคาครับ แต่ยังซื้อสินค้าเหมือนเดิม"
    ก่อน: ดีลถูกยกเลิก
    หลัง: ถอนเฉพาะคำขอใบเสนอราคา ยอดขายยังอยู่


4) ปัญหาเพิ่มเติมที่พบระหว่างตรวจ (แก้แล้ว มี test ครบ)
--------------------------------------------------
- การแบ่งอนุประโยคละเอียดเกินไป
  เช่น "…ใบเสนอราคา PDF ให้แล้ว" ถูกแยกจนไม่รู้ว่าส่งแล้ว
- คำขอเลื่อนแบบสุภาพ "…ได้ไหม" ถูกตีความเป็นคำถาม จนตกหล่น
- เงื่อนไขที่ขึ้นต้นด้วย "แต่ถ้า…" ไม่ถูกนับ
- "ถ้าแพงกว่านี้ผมไม่ซื้อ" ทำให้ยอดขายหายไป
  เพราะถูกนับเป็นการต่อราคา
- ยอดคงเหลือของมัดจำ ถูกบันทึกเป็นการชำระทั่วไป
  (พบจากรอบแรกของ action scenarios)
- คำไม่เป็นทางการ:
  * "เอาจ้า" / "เอาคับ" ไม่ถูกนับว่าตกลง
  * "โอนละนะคะ" / "เสร็จละครับ" ไม่ถูกนับว่าทำแล้ว
  * "หากโอนแล้วจะแจ้ง" ถูกนับเป็นการรอตัดสินใจ
  * คำว่า "ขอบคุณ" ยังไม่ถือว่าตอบข้อเสนอของร้านแล้ว


5) การวัดผลชุดใหม่: action scenarios (24 สถานการณ์)
--------------------------------------------------
ล็อกคำตอบก่อนรัน แต่ละสถานการณ์ตรวจ 4 อย่าง:
- ยืนยันยอดขายถูกต้องหรือไม่
- มี action ที่ต้องมีครบ
- ไม่มี action ที่ห้ามมี
- คำรับปากที่ยังเปิดอยู่ตรงทุกข้อ

รอบแรก (ก่อนแก้):
    ถูกทั้งสถานการณ์ 23/24 (0.958)
    คำรับปากที่เปิดอยู่ถูก 0.958
    ยืนยันยอดขายถูก 5/5
    นับยอดขายผิด 0/19
หลังแก้:
    ถูกทั้งสถานการณ์ 24/24
    (ตัวเลขนี้ไม่ใช่ blind แล้ว)

  จึงไม่ใช่หลักฐานความแม่นยำในโลกจริง
- รีวิวอิสระทุกรอบยังพบกรณีนอกชุดข้อมูล
- ยังไม่ได้วัดความมีประโยชน์ของ action โดยคน


7) จุดอ่อนที่ยังเหลือ
--------------------------------------------------
- ชั้นตีความเหตุการณ์ยังเป็น heuristic ขนาดเล็ก
  แบ่งอนุประโยคจากช่องว่างและคำเชื่อมไม่กี่คำ
- ส่งเอกสารแบบแยกสองข้อความยังไม่ถูกนับว่าส่งแล้ว (ระวังไว้ก่อน)
  เช่น "ส่งใบเสนอราคา" / "ให้แล้วนะครับ"
- การขอเลื่อนที่ไม่ระบุสิ่งของยังไม่ถูกบันทึก
  เช่น "ไว้ค่อยส่งทีหลัง"
- การขอเลื่อนวันส่งใบเสนอราคา: นัดติดตั้งยังถูกต้อง
  แต่ action ส่งใบเสนอราคายังไม่มีวันใหม่ติดไปด้วย
- การคำนวณการโอนบางส่วนใช้เฉพาะยอดที่ระบุในข้อความเดียวกัน
- ยังเป็นกฎภาษาไทย ไม่ใช่ parser
- หนึ่งดีลและหนึ่งนัดต่อหนึ่งบทสนทนา
- ใช้ข้อมูลสังเคราะห์เท่านั้น และค่า confidence ยังไม่ได้ calibrate


8) แผนประเมินกับข้อมูลจริง (PILOT_EVALUATION_PLAN.md)
--------------------------------------------------
- ใช้แชตจริงที่ได้รับความยินยอม (PDPA) และลบข้อมูลส่วนตัว
  โดยมีคนตรวจซ้ำอีกรอบ
- ห้าม commit แชตจริงลง repository หรือใช้ใน CI
- แยกชุด dev กับชุด evaluation ตาม "ร้าน" ไม่ใช่ตามบทสนทนา
- ล็อกชุด evaluation ด้วย hash ก่อนเริ่มใช้
  คนที่แก้กฎห้ามดูชุด evaluation
- ให้คนสองคน label แยกกัน มีคนตัดสินเมื่อเห็นต่าง และวัดค่า kappa
- ให้ร้านค้าให้คะแนน action แต่ละรายการ:
  มีประโยชน์ / ถูกแต่ไม่จำเป็น / ผิด / อันตราย
- เป้าหมาย:
  * นับยอดขายผิด < 3% (รายงานขอบบนด้วย)
  * action ที่มีประโยชน์ >= 80%
  * action อันตราย = 0
- ขนาดข้อมูล:
  ต้องมีบทสนทนาที่ไม่ใช่ยอดขายราว 300 บทขึ้นไป
  ขอบบนของอัตราขายผิดถึงจะต่ำกว่า 1% ได้
